## Reference baseline

Amazon’s homepage is personalized by location, account state, season, and active promotions. The clone should therefore reproduce the stable US Amazon shopping system—not a single transient promotion.

Direct automated access to Amazon’s homepage currently triggers its JavaScript/robot-verification screen. ## 1. Recommended stack

| Concern | Recommendation | Reason |
|---|---|---|
| Application | React + TypeScript + Vite | Fastest route to a polished SPA; no SSR or backend requirement in the assignment. |

## 2. Architecture

Use a feature-oriented client application with static catalog data:

```text
Static catalog + homepage configuration
                 │
                 ▼
       Catalog selectors/search
                 │
      ┌──────────┼───────────┐
      ▼          ▼           ▼
   Homepage   Results       PDP
                              │
                              ▼
                    Cart reducer/context
                              │
                    localStorage persistence
                              │
                              ▼
                            Cart
```

Key decisions:

- URL parameters are the source of truth for query, sort, and filters.
- The cart stores product IDs, selected variants, and quantities—not duplicated product data.
- Pages read product details from the catalog by ID.
- Prices are stored as integer cents.
- Domain calculations stay outside components.
- No API layer, database, authentication, or checkout backend.
- Separate visually different Amazon patterns instead of forcing one universal product-card component.

## 10. Responsive strategy

Use content-driven CSS with three main modes:

| Viewport | Behavior |
|---|---|
| `< 768px` | Mobile header; full-width search row; horizontal category navigation; no permanent filter sidebar; stacked PDP; compact cart rows; one-column homepage sections or horizontal rails. |
| `768–1023px` | Two-column homepage modules; compact header controls; filter drawer; PDP gallery and information followed by full-width buy box. |
| `≥ 1024px` | Full two-tier header; filter sidebar; four-column homepage promotions; three-column PDP; cart plus sidebar summary. |

Implementation principles:

- Reorder content semantically rather than relying on unsafe visual-only ordering.
- Use CSS Grid for macro layouts and Flexbox for compact controls.
- Use `minmax(0, 1fr)` to prevent long titles from producing overflow.
- Keep product image aspect ratios stable.
- Lazy-load below-the-fold images; eagerly load only the logo and hero.
- Use `clamp()` sparingly for major spacing, not for every font size.
- Maintain 44px touch targets on mobile.
- Do not hide commerce-critical metadata merely to make mobile cleaner.

## 11. Major risks

| Risk | Mitigation |
|---|---|
| Scope expansion | Lock P0 early; no P1 work until the complete flow is functional. |
| Looking like a generic store | Prioritize header proportions, listing rows, buy box, typography density, delivery text, ratings, Prime badges, and page backgrounds. |
| Amazon changes by session/location | Select one anonymous US desktop/mobile baseline and remain internally consistent. |
| Asset quality or copyright | Use curated local demo assets with documented sources; do not scrape or hotlink. |
| Too many products | Use fewer, better-authored products rather than hundreds of weak fixtures. |
| Mid-width breakage | Test continuously at 768, 900, and 1024px—not only phone and desktop. |
| Cart state defects | Central reducer, derived totals, local-storage validation, focused unit tests. |
| Performance from images | Pre-size, compress, use WebP, lazy-load, and avoid oversized hero assets. |
| Trademark/phishing appearance | Keep checkout and login non-functional; identify it as an educational hiring-assignment clone in the README and deployment footer. |
| Last-minute deployment issues | Deploy a shell early and test SPA route rewrites before feature completion. |
